# remove_001 评测优化实验：第 2 轮

## 实验目标

减少连续工具调用带来的历史消息膨胀，让 Agent 在有限 token 预算内保留可用证据并继续执行后续轮次。

## 本轮改动

- 为 `_create_dev_agent` 增加可选的 `convergence_tool_steps` 参数。
- 仅在 remove_001 中将上下文收敛阈值设为 8 次工具调用；生产交互默认值仍为 25。
- 达到阈值后保留最近工具步骤和证据摘要，压缩旧的 ReAct 历史。

## 评测结果

用例：`trace-3-1-component-element-continuous-remove-001`

| 指标 | 第 2 轮 |
|---|---:|
| 状态 | `budget_exceeded` |
| 通过 | 否 |
| 得分 | `0.1628` |
| 耗时 | `61.5s` |
| 工具调用 | `22` |
| token 统计 | `100,123` |

### 轮次情况

- 第 1 轮：问候，无工具调用。
- 第 2 轮：组件查询，10 次工具调用，得到正确的 4 个 `CompElement` 名称。
- 第 3 轮：12 次工具调用后进入 `reserve_finalization_empty_response`，尝试了 UML 编辑但没有完整完成后续流程。
- 第 4 轮：进入 `reserve_finalization`，未执行源码同步。
- 第 5～7 轮：达到 `hard_limit_before_next_llm`，没有继续调用模型工具。

最终 UML 有效性和 pytest 通过，但最终组件集合、源码同步、文件清理和自动审核未全部通过。

## 与第 1 轮对比

- 工具调用：`16 → 22`，多获得了 6 次有效工具调用。
- 耗时：`68.8s → 61.5s`，减少约 7.3 秒。
- 得分：`0.1163 → 0.1628`，有所提升。
- 预算状态：由 `budget_finalized` 变为 `budget_exceeded`，说明压缩后 Agent 更充分地使用了预算，但仍没有在预算内完成任务。

## 结论

提前上下文压缩方向有效，但每次模型调用仍携带较大的工具 schema 和当前历史。下一轮应压缩重复的工具参数说明，同时保持工具名称、参数类型和关键约束可见，以降低每次 LLM 请求成本。
