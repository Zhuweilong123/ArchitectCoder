# remove_001 三轮评测优化总对比

用例：`trace-3-1-component-element-continuous-remove-001`

## 结果总览

| 阶段 | 状态 | 通过 | 得分 | 耗时 | 工具调用 | token |
|---|---|---:|---:|---:|---:|---:|
| 历史基线* | 旧汇总逻辑下显示通过 | 是* | — | 271.5s | 94 | 406,378 |
| 第 1 轮 | `budget_finalized` | 否 | 0.1163 | 68.8s | 16 | 102,949 |

\* 历史基线的“通过”没有纳入所有轮次的硬校验，不能作为真实完成度；本轮实验使用修正后的汇总逻辑重新判定。

## 三轮改动脉络

1. 第 1 轮通过系统提示和工具描述约束，减少无效探索和错误后的重复探测。
2. 第 2 轮只对 remove_001 收紧上下文收敛阈值，使 Agent 更早保留最近证据，减少历史膨胀。
3. 第 3 轮压缩重复工具 schema，首次请求保留完整说明，后续请求保留调用形状，收尾阶段不再携带工具 schema。

三轮均未增加主 Agent 工具数量；也没有启用子代理。

## 趋势与判断

- 相比历史基线，耗时从 `271.5s` 降至 `55.0s`，减少约 `79.7%`。
- token 从 `406,378` 降至 `99,040`，减少约 `75.6%`。
- 工具调用从 `94` 降至 `20`，减少约 `78.7%`。
- 得分在第 2 轮提升后于第 3 轮持平，三轮都没有完成用例。
- 第 2 轮获得了更高得分，但出现独立的 `budget_exceeded`；第 1、3 轮为 `budget_finalized`。预算超限和主动收尾已经能够被独立记录，不再与超时、普通失败混淆。

## 总结

当前优化已明显解决成本和耗时问题，但完成度没有同步提升。第 3 轮说明继续压缩 schema 的收益有限；真正需要优化的是连续任务的执行编排：让 Agent 在同一轮或明确的共享检查点内完成“修改 UML → 同步源码 → 清理文件 → 运行验证 → 审核”的闭环，并在预算临界前优先完成硬校验要求。
