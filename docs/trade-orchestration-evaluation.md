# project_trade 多智能体编排专项评测

## 目标与固定任务

本评测以 `project/project_trade` 的设计、源码、测试快照为独立 fixture，要求修复已支付且未发货订单取消时的退款、库存回补、幂等性及日报/月报统计。两个 Prompt 变体共享相同隐藏测试、原有项目测试和 UML 文件保护：`trade-orchestration-paid-cancel-001` 观察自然诉求是否触发调度；`trade-orchestration-demand-001` 明确提出架构探索诉求，观察调度启动后的效果。两种结果分别分析，不合并通过率或耗时。

该任务涉及 `SalesService`、`InventoryService`、`ReportService`、`Order` 和 `Payment`。它适合观察跨组件探索的效果，但项目规模较小，结果不能外推到超大型代码仓。

## 对照组

| 组 | 编排 | 架构调度 | 主 Agent 通用子代理 |
|---|---|---|---|
| A | 关闭 | 关闭 | 关闭 |
| C | 开启 | 主 Agent 按需请求 | 关闭 |

A/C 使用相同模型、生产预算、用户 Prompt、评测 fixture 与隐藏验收。每次运行物化新的工作区，先同步构建设计层与源码层图谱。Runner 将图谱索引耗时记在 `graph_preindex.index_ms`；比较报告同时给出包含索引的总耗时和扣除索引的 Agent 耗时。每组使用独立 Python 进程，避免 Settings 缓存导致配置串组。旧批次的 B 组数据保留，但不纳入后续决策。

## 运行与结果

在可以导入 `extensions` 和 `backend/app` 的环境中，先运行一次每组的试运行，再执行重复比较：

```text
python -m extensions.evals.orchestration_compare --repeats 1
python -m extensions.evals.orchestration_compare --case-id trade-orchestration-demand-001 --repeats 1
python -m extensions.evals.orchestration_compare --repeats 10
python -m extensions.evals.orchestration_compare --case-id trade-orchestration-demand-001 --repeats 10
```

脚本交错安排 A/C 的顺序，并写入 `temp/evals/orchestration_compare/<批次>/`。`manifest.json` 记录配置、fixture 哈希及相关实现文件哈希，`results.jsonl` 保存原始评测结果，`traces/` 保存完整 Trace，`summary.json` 保存逐次指标与分组中位数。执行失败会留下错误记录；不要把缺失结果计为零成本或通过。

## 指标解释

- **质量门槛**：隐藏验收、项目原有测试、受保护路径全部通过。是否调用 `explore_architecture` 不作为通过条件。
- **端到端成本**：总耗时、Agent 耗时、Trace 汇总 Token、工具调用数和失败类别。
- **编排行为**：诉求触发率、调度工具耗时、实际子 Agent Token、工作项完成/部分/失败数、有文件工具证据的工作项数、执行槽的最大/平均负载比及发生重分区的计划数。
- **主 Agent 探索负担**：首次修改前的 `read_file` 次数、不同文件数及返回文本字符数；C 组另统计委派前的读取次数/文件数和委派后重复读取先前文件的次数。返回文本字符数受工具输出裁剪影响，只代表主 Agent 实际收到的内容。
- **归因限制**：`worker_tokens` 是调度器报告的子 Agent 用量，用于解释总 Token，不与 Trace 的 `total_tokens` 直接相加。只有一条任务、每组少量重复时，中位数只能作为探索性证据；扩大结论须加入不同任务及更大项目。

首次比较先检查 C 组是否实际触发探索、图谱是否有有效设计和源码节点、报告是否有具文件证据的结果。若这些条件不成立，应先修复评测环境或图谱覆盖，再解释 A/C 的性能差异。正确性低于基线时，不能仅凭耗时下降判定编排有效。

## 首次试运行观察（2026-09-27）

自然诉求变体的首次运行中，A/C 均通过业务验收，端到端分别为 82.6/72.4 秒，总 Token 分别为 580579/652732。C 未调用 `explore_architecture`。收紧“三个及以上组件”提示后单独复跑 C，仍未调用该工具。因此这些自然任务运行**没有覆盖动态调度器**，不能把 C 的耗时差异解释为多 Agent 收益。

显式诉求变体单独运行 C：触发 1 次调度，产生 4 个工作项，实际子 Agent 用量 12887 Token，4 项均为 `partial` 且没有子 Agent 文件工具证据；报告的执行槽最大/平均耗时比为 1.017。原始评测结果为失败，原因是第一版隐藏断言额外要求重复取消返回 `False`。该断言已改为检查退款调用和库存记录是否重复；使用修订后的隐藏测试检查这次保存的产物，4 项全部通过。原始结果保留，不追改为成功。

这些数据只证明评测链路、分区和委派可以运行，也暴露了自然触发率与证据质量问题。正式量化比较需在固定代码与修订后的检查器上重跑两个变体的 A/C 多次，并分别报告质量和成本。`EvalResult.total_tokens` 是多轮 Trace 的累计用量；用例的 `max_total_tokens` 字段并非普通用例的生产累计预算，不能把它当成该值的硬上限。

修订后的显式诉求变体完成了一轮试运行，结果存于 `temp/evals/orchestration_compare/20260927_233008_055e30/`。以下只列 A/C：

| 组 | 隐藏与原项目验收 | 总耗时 | Trace 总 Token | 委派子 Agent Token | 诉求工具调用 |
|---|---|---:|---:|---:|---:|
| A | 通过 | 110.8 秒 | 663499 | 0 | 0 |
| C | 通过 | 123.3 秒 | 636678 | 13108 | 1 |

C 的 4 个只读工作项均为 `partial`：它们带有预取文件摘录，却没有子 Agent 自己调用文件工具的证据；执行槽最大/平均耗时比来自一次调度，不构成稳定的均衡性结论。这一轮 C 相对 A 耗时多约 11.2%、总 Token 少约 4.0%。单次波动和证据不足使这些差异只能作为后续重复评测的假设，不能作为推广阈值。

## 按需探索优化与复评（2026-09-28）

主 Agent 在跨组件任务中先用需求、项目图谱或最多两次定点源码读取形成具体探索诉求，再调用 `explore_architecture`；返回后读取真正的修改点和未解决依赖。首轮评测使用 18000 Token、两个分区工作项，其中一个子 Agent 因累计额度不足停止；24000 Token 定向复跑中仍有一个工作项在形成摘要前停止。现将默认共享额度调至 32000 Token，每项约 16000 Token；只有共享预算足以给四项各留约 12000 Token 时才拆出后续波次。子 Agent 的收尾预留配置为 1000 Token（通用运行时检查仍有 2500 Token 下限），并被明确要求先用文件工具核对目标方法。预取摘录优先定位方法/类定义，输出可直接用于工具的工作区相对路径。达到预算后会返回已取得的文件工具坐标与未解决状态，不丢弃证据。

先以 18000 Token 完成一轮 A/C 对照，两个任务变体的四次运行均通过业务验收：

| 用例 | 组 | 总耗时 | Trace 总 Token | 首次修改前主 Agent 读文件次数/不同文件数 | 探索诉求 |
|---|---|---:|---:|---:|---:|
| 自然诉求 | A | 102.6 秒 | 587639 | 21 / 16 | 0 |
| 自然诉求 | C | 82.2 秒 | 437836 | 17 / 15 | 0 |
| 显式诉求 | A | 106.6 秒 | 784712 | 21 / 15 | 0 |
| 显式诉求 | C | 111.0 秒 | 656420 | 17 / 14 | 1 |

自然诉求 C 仍未触发动态调度，不能把耗时差异归因于编排。显式诉求 C 在启动 3 次 `read_file` 后调用工具；2 个工作项中 1 个有成功的文件工具证据，另 1 个触及累计额度，原实现丢弃其已读证据并标为失败。批次分别为 `20260928_001332_768949` 和 `20260928_001659_7f593d`。

修正工作区相对路径提示后，以 24000 Token 单独复跑 C（`20260928_002440_848a77`）：业务验收通过、112.6 秒、517014 Trace Token，主 Agent 在读文件前发起探索；两个工作项都有文件工具证据，其中一个形成完整报告，另一个仍在最终摘要前触及累计额度。随后将默认共享额度调至 32000 Token，并在额度停止时保留已取得的文件工具坐标，状态标为 `partial`。

32000 Token 的 C 定向复跑（`20260928_091647_c44b09`）也通过业务验收：120.2 秒、996683 Trace Token，两个工作项都有文件工具证据，分别为 `completed` 和 `partial`，没有失败项。但主 Agent 在发起探索前已经读取 23 次、17 个不同文件，影响子图也被标记为截断。这说明**证据保留和路径可用性改善了，早期触发与减少主 Agent 阅读仍不稳定**。后两次是 C 单组定向复跑，不能与先前 A 组单次结果作严格性能归因。下一步应先稳定诉求触发时机，再在固定代码上重复 A/C 比较。

## 轻量图谱路由决策与 C 单组试跑

C 组在 `prepare()` 阶段读取有界图谱地图，只提供候选图名、类名与图规模；这些名称不代表已确认的影响范围。主 Agent 遇到跨组件或依赖不清的任务时，可调用 `route_architecture(decision, reason, goal?, search_queries?)` 记录决策：`direct` 只返回定点查找建议，不启动子 Agent；`explore` 调用原有图谱调度。局部明确任务可以直接执行。原 `explore_architecture` 入口保留，以兼容显式诉求和旧调用。

比较脚本新增路由决策率、直接查找率、决策原因记录率和决策前主 Agent 读文件次数；真正的探索调用率、工作项证据及成本仍单独统计。
